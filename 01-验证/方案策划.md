# HubForge — Vibecoding 统一应用门户框架

> **用途**: 为传统企业业务人员的 vibecoding 应用提供统一入口、统一用户/权限管理、多租户隔离
> **填写人**: 策划师
> **版本**: v1.0 | **日期**: 2026-07-23

---

## 一句话概述

> HubForge 是一个多租户应用门户框架，让 vibecoding 产出的应用以插件形式一键接入，统一用户/组织/权限/入口，一个域名管所有应用。

---

## 为什么要做 (Why)

### 问题/痛点

1. **vibecoding 产出碎片化** — 业务人员用 AI 各做一个 H5 小工具，没有统一入口，用户要记 N 个网址
2. **用户管理重复建设** — 每个 vibecoding 应用都要自己做登录、注册、权限，重复劳动且不统一
3. **企业形象不统一** — 每个应用各自一套 UI 风格，对外显得不专业
4. **权限管理失控** — 没有统一的权限中心，主管理员无法掌控各应用的用户访问
5. **部署和运维成本高** — 每个应用独立部署、独立域名，管理成本随应用数线性增长

### 市场机会

- **市场规模**: vibecoding 浪潮下，非程序员（业务人员、产品经理、运营）正在批量产出 AI 辅助应用。据 GitHub Copilot 数据，AI 辅助编程用户已超 200 万；Cursor 等工具进一步降低门槛，目标用户群体从开发者扩展到所有知识工作者
- **趋势**: 从"AI 帮你写代码"到"AI 帮你做应用"，vibecoding 正在从开发者工具变成业务工具
- **竞争格局**:
  - 低代码平台（钉钉宜搭、明道云）— 封闭生态，应用无法脱离平台运行
  - 开源方案（Supabase + Next.js）— 太技术化，业务人员搞不定
  - 企业中台 — 大厂才有，中小企业没有资源建设
  - **空白**: 没有专门面向 vibecoding 场景的"应用容器"
- **时机**: 现在正是 vibecoding 工具成熟但应用管理缺失的窗口期，先占位者有先发优势

### 价值主张

| 受益方 | 带来什么价值 | 量化指标 |
|-------|------------|---------|
| 业务人员 | vibecoding 出的应用有地方放、有统一入口、不用管用户系统 | 应用上线时间从 N 天→1 天 |
| IT 管理员 | 一个后台管所有应用的用户和权限 | 管理成本与应用数量解耦 |
| 最终用户 | 一个入口访问所有内部应用 | 记住 1 个账号 + N 个应用 |
| 企业 | 统一品牌、统一数据、统一安全 | 内部工具标准化率 100% |

### 不做的风险

- vibecoding 产出越来越多，碎片化只会加剧，最后变成"应用坟场"
- 每个应用各自一套用户体系，安全隐患随数量增长
- 企业对 vibecoding 产出失去信心，认为"不上档次"

## 怎么做 (How)

### 方案概述

> HubForge 是一个多租户应用门户框架——它本身是一个完整的 Web 应用（PC + H5），提供用户/组织/权限/应用管理；vibecoding 产出的应用以"应用模块"形式挂载到框架下，通过配置注册权限，由框架统一控制入口和鉴权。

（名字寓意：Hub = 枢纽/中心，Forge = 锻造——在这里锻造你的所有应用）

### 核心设计原则（第一性原理）

1. **一个入口** — 用户只需记住一个域名，所有应用在框架内导航
2. **一套账号** — 统一认证（SSO），一次登录访问所有应用
3. **两层权限** — 框架权限（主租户控制）+ 应用权限（各租户自治）
4. **零侵入集成** — vibecoding 应用不改代码，通过配置接入
5. **多租户隔离** — 每个租户独立数据域、独立用户池、独立权限管理
6. **简单易用** — 业务人员能自助完成应用接入，不需要技术人员介入

### 实现路径

| 步骤 | 做什么 | 产出 | 预计时间 |
|------|--------|------|---------|
| 1 | 架构设计 | 技术方案文档 + 数据库设计 + 接口规范 | 3 天 |
| 2 | 框架核心开发 | 用户/组织/租户/权限模块 | 2 周 |
| 3 | 应用管理模块 | 应用注册、配置、路由嵌入、iframe沙箱 | 1 周 |
| 4 | H5 端适配 | 响应式布局 + H5 导航 + 移动端优化 | 3 天 |
| 5 | 应用集成规范 | 编写 vibecoding 应用接入文档 + SDK | 2 天 |
| 6 | 内部测试 + Demo | 接入 1-2 个 vibecoding 应用验证 | 3 天 |

### 技术路径

| 维度 | 选择 | 理由 |
|------|------|------|
| 前端框架 | Next.js (React) | 生态成熟，SSR 支持好，vibecoding 最常用的技术栈（Cursor/Copilot 对 React 支持最好） |
| 后端 | Next.js API Routes + Prisma | 全栈统一，减少技术栈复杂度，适合一人公司维护 |
| 数据库 | PostgreSQL | 多租户数据隔离（Schema per tenant 或 Row Level Security），JSON 字段支持，成熟稳定 |
| 认证 | NextAuth.js + JWT | 开箱即用的认证方案，支持多种 Provider |
| 应用嵌入 | 同域 iframe 沙箱 + postMessage 通信 | 零侵入，vibecoding 应用不需改代码即可接入 |
| 样式 | Tailwind CSS + shadcn/ui | 快速搭建统一 UI，vibecoding 工具对该组合生成质量最高 |
| 部署 | Docker + Nginx 反向代理 | 单域名多应用路由，运维简单 |

### 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| iframe 沙箱兼容性问题 | 中 | 中 | 同域部署避免跨域问题；备选方案：postMessage 通信 + API 网关 |
| vibecoding 应用质量参差不齐 | 高 | 中 | 提供应用接入规范 + 最低质量标准（必须有入口页面、必须响应框架鉴权） |
| 多租户数据泄露 | 低 | 高 | PostgreSQL Row Level Security + 中间件强制过滤租户 ID |
| 性能瓶颈（iframe 多应用） | 中 | 中 | 懒加载 iframe + 按需激活应用 + 单页面只加载一个应用 |
| Next.js 全栈方案复杂度 | 低 | 中 | 用成熟模板（T3 Stack）起步，避免从零搭建 |

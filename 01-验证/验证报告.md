# HubForge 想法验证报告

> **调研员**: AI 调研员 | **日期**: 2026-07-23
> **结论**: ✅ GO — 无直接竞品，技术可行，建议基于 qiankun + 自研门户壳构建

---

## 1. 想法概述

- **一句话描述**: 为传统企业业务人员的 vibecoding 应用提供统一门户框架，统一用户/权限/入口
- **目标用户**: 传统企业 IT 管理员 + 业务人员（用 AI 工具做应用的非程序员）
- **核心问题**: vibecoding 产出碎片化，无统一管理，每个应用重复建设用户/权限系统
- **解决方案**: HubForge 多租户应用门户 + 应用开发规范，让 vibecoding 应用即能独立演示也能嵌入统一门户

---

## 2. 市场分析

- **市场规模**: vibecoding 浪潮下，非程序员开发应用的群体正在快速增长。Cursor/Claude Code/Copilot 等工具用户已超百万级别
- **增长趋势**: 从"AI 帮你写代码"到"AI 帮你做应用"，vibecoding 正从开发者工具变成业务工具
- **主要玩家**: 低代码平台（钉钉宜搭、明道云）= 封闭生态；企业中台 = 大厂专属

## 3. 竞品分析

### 3.1 微前端框架对比

| 框架 | GitHub Stars | 组织 | 核心技术 | 沙箱隔离 | 双模运行 | 与 HubForge 差距 |
|------|-------------|------|---------|---------|---------|---------------|
| **qiankun** | 16.6k | 蚂蚁集团 | JS Sandbox + HTML Entry | Proxy Sandbox | ✅ | ❌ 不含门户UI/权限/多租户 |
| **single-spa** | 13.9k | 社区 | 路由劫持 + 生命周期 | ❌ 无沙箱 | ✅ | ❌ 无沙箱，技术门槛高 |
| **micro-app** | 6.2k | 京东 | Web Component + 类iframe | iframe 沙箱 | ✅ | ❌ 不含门户/权限/多租户 |
| **wujie** | ~5k | 腾讯 | Web Worker + iframe | 完全隔离 | ✅ | ❌ 强隔离但无门户功能 |
| **Garfish** | 2.9k | 字节跳动 | VM Sandbox | Proxy Sandbox | ✅ | ❌ 字节内部使用，生态封闭 |
| **Piral** | 1.9k | smapiot | App Shell + 微前端 | iframe/自定义 | ✅ | ⭐ 最接近，但缺多租户和 vibecoding 集成 |
| **Luigi** | 921 | SAP | App Shell + iframe | iframe 隔离 | ✅ | ⭐ 接近，但面向 SAP 生态 |

### 3.2 核心结论

**市场上没有"vibecoding + 应用门户 + 多租户"的直接竞品。**

- 微前端框架（qiankun 等）只解决"应用加载和沙箱"，不含门户 UI、权限管理、多租户
- Piral/Luigi 有 App Shell 概念，但缺少多租户和 AI 工具链集成
- HubForge 的差异化：**专门为 vibecoding 场景设计**，含应用开发规范 + 统一门户 + 多租户 + 双模运行

## 4. 技术方案评估

### 4.1 应用嵌入技术对比

| 方案 | 隔离性 | 接入成本 | URL同步 | 用户体验 | 推荐度 |
|------|--------|---------|---------|---------|--------|
| **iframe** | ⭐⭐⭐⭐⭐ 完全隔离 | ⭐⭐⭐⭐⭐ 零改造 | ❌ 需额外处理 | ⭐⭐ 滚动/弹窗问题 | 备选 |
| **qiankun 微前端** | ⭐⭐⭐⭐ JS/CSS沙箱 | ⭐⭐⭐ 需配置生命周期 | ✅ 自动同步 | ⭐⭐⭐⭐ 无缝 | **推荐** |
| **micro-app** | ⭐⭐⭐⭐ Web Component | ⭐⭐⭐⭐ 类iframe低成本 | ✅ 支持 | ⭐⭐⭐⭐ 无缝 | 备选 |
| **wujie** | ⭐⭐⭐⭐⭐ Worker隔离 | ⭐⭐⭐⭐⭐ 零改造 | ✅ 支持 | ⭐⭐⭐⭐ 无缝 | 强隔离场景 |

### 4.2 双模运行架构（核心设计）

**关键需求**：应用既能独立运行（开发/演示），也能嵌入 HubForge（生产）。

```
┌─────────────────────────────────────────────┐
│  vibecoding 应用                              │
│                                              │
│  entry.ts:                                   │
│  if (window.__POWERED_BY_HUBFORGE__) {       │
│    // 嵌入模式：导出生命周期给宿主              │
│    export { bootstrap, mount, unmount }       │
│  } else {                                    │
│    // 独立模式：直接挂载渲染                   │
│    createApp(App).mount('#app')              │
│  }                                            │
└─────────────────────────────────────────────┘
```

此模式被 qiankun、single-spa、Garfish、icestark 等主流框架验证，是成熟方案。

### 4.3 推荐技术路线

```
┌─────────────────────────────────────────────┐
│              HubForge 门户壳                  │
│  统一导航 │ 权限管理 │ 多租户 │ 应用市场       │
├─────────────────────────────────────────────┤
│         qiankun 微前端加载层                   │
│  - 应用生命周期管理                            │
│  - JS/CSS 沙箱隔离                            │
│  - 路由同步                                   │
│  - 应用间通信（props/全局状态）                 │
├─────────────────────────────────────────────┤
│         vibecoding 应用（子应用）               │
│  - 双模入口（standalone / embedded）           │
│  - 遵循 HubForge 应用开发规范                  │
│  - 独立可运行，嵌入可集成                       │
└─────────────────────────────────────────────┘
```

**技术选型确认**：

| 维度 | 选择 | 理由 |
|------|------|------|
| 微前端运行时 | qiankun | 最成熟（16.6k stars），沙箱+路由+生命周期完整 |
| 前端框架 | React (Next.js) | vibecoding 工具对 React 支持最好 |
| 子应用支持 | React/Vue/Angular 均可 | qiankun 框架无关 |
| 数据库 | PostgreSQL | Row Level Security 多租户隔离 |
| 认证 | NextAuth.js + JWT | 标准方案 |

## 5. CEO 批示落实：应用开发规范约束

CEO 指示：**"要关注对 vibecoding 应用开发规范的约束，后续都会按照 HubForge 开发，即可单独演示，可以嵌入 HubForge 进行实战对外演示"**

### 5.1 应用开发规范设计（初步）

**核心思路**：提供一个 vibecoding 脚手架模板（scaffold），让 Cursor/Claude Code 直接生成符合规范的应用。

**规范要点**：

1. **入口文件规范** — `src/index.tsx` 必须检测 `window.__POWERED_BY_HUBFORGE__`，决定 standalone/embedded 模式
2. **路由规范** — standalone 模式自带路由；embedded 模式由宿主控制路由前缀
3. **配置文件** — `hubforge.config.json` 声明应用元数据（名称、图标、权限需求、路由规则）
4. **API 认证** — embedded 模式下，框架注入 JWT token；standalone 模式下，应用自行处理认证
5. **样式规范** — CSS 隔离由 qiankun 沙箱处理；应用不污染全局样式
6. **权限声明** — 在 `hubforge.config.json` 中声明所需权限，框架统一控制

### 5.2 hubforge.config.json 示例

```json
{
  "name": "我的vibecoding应用",
  "version": "1.0.0",
  "icon": "/icon.png",
  "entry": "/src/index.tsx",
  "routes": [
    { "path": "/", "title": "首页" },
    { "path": "/settings", "title": "设置" }
  ],
  "permissions": [
    { "key": "app.view", "label": "查看", "type": "framework" },
    { "key": "app.edit", "label": "编辑", "type": "app" }
  ],
  "menuPosition": 10,
  "standalone": {
    "port": 3001,
    "auth": "local"
  }
}
```

**权限类型说明**：
- `type: "framework"` — 框架权限，由主租户控制（如"谁能访问这个应用"）
- `type: "app"` — 应用权限，由租户自己控制（如"谁能编辑数据"）

### 5.3 脚手架计划

计划提供 `create-hubforge-app` 脚手架命令：

```bash
npx create-hubforge-app my-app
# 自动生成：
# - 双模入口文件
# - hubforge.config.json
# - 标准目录结构
# - 开发/构建/部署脚本
# - README（含接入指南）
```

## 6. 可行性评估

- **技术难度**: 中 — 微前端方案成熟，qiankun 有大量生产实践
- **预计周期**: 5 周（含框架 + 规范 + Demo）
- **资源需求**: 1 人 + Cursor + 云服务器
- **成本**: ¥550/年（域名+云服务）

---

## 7. 风险

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| qiankun 对 Next.js SSR 支持有限 | 中 | 中 | 子应用用 CSR 模式，HubForge 门户壳用 SSR |
| 应用开发规范太复杂，业务人员搞不定 | 中 | 高 | 提供脚手架模板 + Cursor Rules 文件，AI 自动遵循 |
| 多租户数据隔离实现复杂 | 低 | 高 | PostgreSQL RLS，中间件强制过滤 |

---

## 8. 结论

- **推荐**: ✅ GO
- **理由**: 无直接竞品，技术方案成熟（qiankun），双模运行模式被验证，脚手架模板可降低接入门槛
- **建议**: 下一步进入 PRD 设计，重点细化应用开发规范和脚手架模板

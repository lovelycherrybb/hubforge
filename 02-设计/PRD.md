> **产品名称**: HubForge — Vibecoding 统一应用门户框架
> **版本**: V1.0
> **撰写人**: 设计师（AI）
> **撰写日期**: 2026-07-23

## 1. 概述

### 1.1 背景

vibecoding（AI辅助编程）浪潮下，传统企业业务人员能用 Cursor/Claude Code 等工具快速产出应用。但这些应用碎片化严重——各自独立部署、各自一套用户系统、没有统一入口。企业需要一个"应用容器"来统一管理这些 vibecoding 产出。

### 1.2 目标

| 目标类型 | 目标描述 | 衡量标准 |
|----------|----------|----------|
| 业务目标 | 建立 vibecoding 应用的统一管理平台 | 所有 vibecoding 应用通过 HubForge 统一入口访问 |
| 用户目标 | 业务人员 30 分钟内完成应用接入 | 按文档操作即可，不改应用代码 |
| 技术目标 | 支持 PC 网页应用和 H5 应用双端接入 | 两种类型应用均可独立运行和嵌入运行 |

### 1.3 范围

**V1.0 包含:**
- 多租户管理（租户创建、配置、数据隔离、主租户全局管控）
- 统一用户/组织管理（登录、密码找回、组织架构 CRUD）— **仅邀请制，不支持自注册**
- 两层权限体系（框架权限 + 应用权限）
- 应用管理（应用注册、iframe 嵌入）
- PC Web 端门户（顶部栏 + 首页 + 应用视图）
- H5 移动端门户（应用卡片 + 全屏应用）
- 应用开发规范 + 脚手架模板（create-hubforge-app）
- 应用双模运行支持（standalone 独立运行 / embedded 嵌入运行）

**V1.0 不包含:**
- 移动端原生 App（仅 Web）
- 应用市场/商店（应用审核、评分、付费）
- 消息中心/通知系统
- 数据看板/报表
- 第三方 SSO 对接（如企业微信、钉钉登录）
- 应用间数据互通

### 3.2 功能详情

#### M1: 用户与认证

**功能描述**: 统一的用户登录、登出、密码找回系统。**V1 仅支持邀请制，不支持自注册。**

**认证方案**: JWT token 存储在 httpOnly Cookie 中（同域部署天然共享，iframe 内子应用自动携带，无需额外传 token）。

**功能流程**:
1. 用户访问 HubForge 域名 → 未登录则跳转登录页
2. 输入邮箱 → 查询 user_tenants 获取所属租户列表
3. **多租户检测**：
   - 如果 0 个租户 → 提示"该邮箱未被任何租户邀请"
   - 如果 1 个租户 → 直接进入密码输入页
   - 如果多个租户 → 跳转租户选择页
4. 用户选择租户（或单租户自动选择）→ 进入密码输入页
5. 输入密码 → 查询 user_tenants 验证该租户下的密码
6. 密码正确 → 签发 JWT（含 tenant_id）→ 写入 httpOnly Cookie
7. 密码错误 → 提示"密码错误"（不透露其他租户信息）
8. 后续请求自动携带 Cookie → 中间件校验
9. Cookie 过期 → 自动刷新（滑动过期 24h）
10. iframe 内子应用同域，自动共享 Cookie，无需额外处理

**租户选择器设计**:

```
┌─────────────────────────────────────┐
│       选择你要访问的租户              │
│                                     │
│  ┌────────────┐  ┌────────────┐    │
│  │  🏢 Acme   │  │  🏭 Bee    │    │
│  │  IT管理员   │  │  普通员工   │    │
│  └────────────┘  └────────────┘    │
│                                     │
│    记住我的选择（30天）               │
└─────────────────────────────────────┘
```

- 选择后，设置 `current_tenant_id` 到 Cookie
- 可选：勾选"记住我的选择"，30 天内自动进入该租户
- 顶部栏显示当前租户名称，点击可切换

**忘记密码流程**:
1. 用户在登录页点击"忘记密码"
2. 输入邮箱 → 系统检测所属租户列表
3. 如果多个租户 → 先选择要重置密码的租户
4. 系统发送验证码邮件（6 位数字，15 分钟有效）
5. 用户输入验证码 → 设置新密码
6. 新密码存入 user_tenants.password_hash（仅重置该租户下的密码）
7. 旧 Cookie 失效 → 重新登录

**租户管理员邀请流程**:
1. 主租户创建租户 → 填写管理员邮箱
2. 系统检查 users 表：
   - 如果邮箱已存在 → 直接在 user_tenants 添加记录（role=admin）
   - 如果邮箱不存在 → 创建 users 记录 + user_tenants 记录
3. 发送邀请邮件 → 用户点击链接设置密码（该租户独立密码）
4. 管理员首次登录 → 进入租户管理后台

**验收标准**:
- [ ] 支持邮箱→选租户→密码的两步登录流程
- [ ] JWT 存 httpOnly Cookie，有效期 24h（滑动刷新）
- [ ] 多租户用户登录后显示租户选择器
- [ ] 单租户用户登录后直接进入密码页
- [ ] 记住我的选择功能（30天有效），失效时自动清除
- [ ] 顶部栏显示当前租户，可切换（切换后跳首页）
- [ ] 忘记密码：先选租户，再重置该租户下的密码
- [ ] 登出后 Cookie 清除
- [ ] 错误密码 5 次后锁定该租户 15 分钟（不影响其他租户）
- [ ] 租户管理员可邀请用户（输入邮箱+角色）
- [ ] 被邀请用户收到邮件后设置密码
- [ ] 未被邀请的邮箱无法登录（提示"该邮箱未被任何租户邀请"）
- [ ] iframe 内子应用自动共享认证状态（同域 Cookie）

#### M2: 多租户

**功能描述**: 支持多个租户（组织/部门），每个租户有独立的数据域。用户通过 user_tenants 表关联到多个租户。主租户拥有全局管控能力。

**主租户管理后台（主租户专属）**:

主租户管理员登录后，顶部栏显示"管理"入口（齿轮图标），包含：

| 管理功能 | 说明 | 优先级 |
|----------|------|--------|
| 租户总览 | 所有租户列表、状态、用户数、应用数 | P0 |
| 租户创建 | 创建新租户，填写名称、配额、管理员邮箱 | P0 |
| 租户配置 | 修改租户基础信息、功能开关、配额限制 | P0 |
| 租户停用/启用 | 临时冻结或恢复某个租户 | P1 |
| 变更租户管理员 | 更换租户管理员账号 | P1 |
| 全局应用管理 | 查看所有租户的应用接入情况 | P1 |
| 全局用户统计 | 各租户用户数量、活跃度概览 | P2 |

**租户配额定义**:

| 配额维度 | 说明 | 默认值 |
|----------|------|--------|
| 最大用户数 | 租户下可创建的用户上限 | 100 |
| 最大应用数 | 租户下可注册的应用上限 | 20 |
| 最大组织层级 | 部门树最大深度 | 8 层 |

达到配额上限时，阻止创建并提示"已达到配额上限，请联系管理员扩容"。

**功能流程**:
1. 主租户管理员创建新租户 → 填写名称、配额、管理员邮箱
2. 系统自动创建管理员账号 → 发送激活邮件
3. 管理员激活后登录 → 只看到本租户的用户、组织、应用
4. 数据访问通过中间件自动注入 tenant_id 过滤

**验收标准**:
- [ ] 主租户可创建/编辑/删除/停用租户
- [ ] 主租户可查看所有租户的用户数、应用数等统计
- [ ] 主租户可配置每个租户的配额（用户数/应用数/组织层级）
- [ ] 主租户可变更租户管理员
- [ ] 达到配额上限时阻止创建并提示
- [ ] 租户之间数据完全隔离
- [ ] 租户管理员只能看到本租户数据
- [ ] PostgreSQL RLS 策略生效

#### M3: 组织架构管理

**功能描述**: 每个租户拥有独立的组织架构（部门树），用于管理本租户下的用户归属和权限继承。

**组织架构模型**:

```
租户A
├── 总公司
│   ├── 生产部
│   │   ├── 一车间
│   │   └── 二车间
│   ├── 质检部
│   └── IT部
└── 分公司
    ├── 销售部
    └── 售后部
```

**功能清单**:

| 功能 | 说明 | 端 | 优先级 |
|------|------|-----|--------|
| 部门树 CRUD | 创建/编辑/删除/移动组织节点 | PC | P0 |
| 部门下用户管理 | 将用户分配到部门、调整归属 | PC | P0 |
| 组织架构查看 | PC 端左侧树形 + 右侧详情；H5 端可折叠列表（只读） | PC+H5 | P0 |
| 组织级权限继承 | 给某个部门配置权限，该部门下所有用户自动继承 | PC | P1 |
| 组织架构搜索 | 按部门名称/用户名搜索 | PC | P1 |

> **说明**: H5 端组织架构仅支持查看（P0），管理操作（CRUD）限制在 PC 端。移动端做树形编辑体验差。

**权限继承规则**:
- **取并集**：个人权限 ∪ 组织权限，只要有任一来源授予即生效
- **只做加法**：组织继承的权限不会覆盖个人直接分配的权限
- **无拒绝**：V1 不支持"拒绝"权限，没有授予 = 没有权限

**用户-组织关系**:
- V1：一个用户只属于一个部门（主部门）
- 数据模型预留：user_departments 关联表支持一对多，V1.1 可扩展兼任

**验收标准**:
- [ ] 支持多层级部门树（建议不超过 8 层，软提示）
- [ ] 部门 CRUD 操作正常（含移动节点），仅 PC 端
- [ ] 用户可分配到部门，V1 一个用户一个主部门
- [ ] H5 端可查看组织架构（只读），不可编辑
- [ ] 组织级权限继承生效（取并集，只做加法）

#### M4: 权限体系

**功能描述**: 两层权限——框架权限由主租户控制，应用权限由各租户自治。

**权限模型**:

```
框架权限（主租户控制，存储在全局权限表，不受 RLS 过滤）
├── tenant.admin              — 租户管理员
├── app.[appKey].access       — 访问某个应用
└── app.[appKey].manage       — 在 HubForge 后台管理该应用配置

应用权限（租户自治，存储在租户数据域内）
├── app.[appKey].[permKey]    — 应用内自定义权限
└── 由应用在 hubforge.config.json 中声明，由租户管理员分配
```

**权限冲突规则**:
- **取并集**：用户从个人直接获得的权限 ∪ 从组织继承的权限，合并生效
- **无拒绝**：V1 只支持"授予"，不支持"拒绝"。没有授予 = 桶有权限
- **类型隔离**：租户管理员只能分配 `type: "app"` 的权限，`type: "framework"` 的权限只能由主租户分配（框架层强制校验）

**验收标准**:
- [ ] 主租户可分配框架权限给任何用户
- [ ] 租户管理员可分配应用权限给本租户用户
- [ ] 租户管理员无法分配框架权限（越权拦截）
- [ ] 权限取并集（个人 ∪ 组织），只做加法
- [ ] 应用通过 hubforge.config.json 声明所需权限
- [ ] 权限校验在框架层统一执行

#### M5: 应用管理与门户

**功能描述**: 注册 vibecoding 应用到 HubForge，通过 iframe 嵌入运行。同时提供 PC 和 H5 两种门户界面。

**嵌入方案**: V1 统一使用 iframe 嵌入（零侵入，应用无需改造）。同域部署，httpOnly Cookie 自动共享认证。

**支持的应用类型**:
- **PC 网页应用**: 桌面浏览器访问的管理后台、数据看板、工作台等
- **H5 应用**: 手机浏览器访问的移动工具、表单填报、现场巡检等

**功能流程**:
1. 业务人员用 vibecoding 工具开发应用（遵循 HubForge 开发规范）
2. 应用独立部署到一个 URL（可本地、可服务器）
3. 在 HubForge 后台注册应用 → 填写应用名称、URL、类型（PC/H5/双端）
4. 配置权限声明 → 应用出现在对应用户的门户中

#### M6: 应用开发规范（开发支撑）

**功能描述**: 定义 vibecoding 应用接入 HubForge 的标准，提供脚手架工具。

**嵌入方案说明**: V1 统一使用 iframe 嵌入。应用无需导出生命周期钩子，无需适配微前端框架。只需：

1. 应用可独立运行（有自己的入口页面）
2. 同域部署后通过 iframe 加载即可
3. 认证由 httpOnly Cookie 共享，应用无需额外处理

**hubforge.config.json 规范**:

```json
{
  "name": "设备巡检系统",
  "version": "1.0.0",
  "description": "车间设备日常巡检工具",
  "icon": "/icon.png",
  "type": "h5",
  "routes": [
    { "path": "/", "title": "巡检首页" },
    { "path": "/record", "title": "巡检记录" },
    { "path": "/report", "title": "巡检报告" }
  ],
  "permissions": [
    { "key": "inspection.view", "label": "查看巡检" },
    { "key": "inspection.submit", "label": "提交巡检" },
    { "key": "inspection.approve", "label": "审批巡检" }
  ],
  "standalone": {
    "port": 3001
  }
}
```

**字段说明**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | string | ✅ | 应用名称 |
| type | "pc" / "h5" / "both" | ✅ | 应用类型 |
| routes | array | ✅ | 应用内路由列表 |
| permissions | array | ✅ | 权限声明（应用开发者只声明需要哪些权限，不区分类型。框架管理员在注册时决定哪些是框架权限、哪些是应用权限） |
| standalone.port | number | ✅ | 独立运行端口 |

> **说明**: permissions 中去掉了 `type` 字段。应用开发者只需声明"我需要这些权限"，由框架管理员在注册应用时决定权限类型（框架权限 vs 应用权限），降低开发者认知负担。

**双模运行规范**:

应用可独立运行（开发/演示），也可嵌入 HubForge（生产）。嵌入方式为 iframe，应用无需改造：

- **独立模式**: `npm run dev` 直接运行，有自己的路由和页面
- **嵌入模式**: 部署后由 HubForge 通过 iframe 加载，认证由 Cookie 共享
- **感知嵌入**: 应用可通过 `window.parent !== window` 检测是否在 iframe 中，或通过 HubForge SDK（`@hubforge/sdk`）获取上下文信息

**HubForge SDK（@hubforge/sdk）**:

```typescript
import { useHubForge } from '@hubforge/sdk';

const { isEmbedded, user, tenant } = useHubForge();
// isEmbedded: 是否在 HubForge iframe 中
// user: 当前用户信息（从 Cookie 解析）
// tenant: 当前租户信息
```

## 5. 非功能需求

### 5.1 性能需求
- 页面加载时间: < 2 秒（首屏）
- API 响应时间: < 500ms
- iframe 应用加载: 取决于应用本身，框架侧 < 100ms

### 5.2 安全需求
- 认证: JWT token 存 httpOnly Cookie（同域共享，防 XSS）
- 密码: bcrypt 加密存储
- 权限: 框架层统一校验，应用层二次校验
- 数据隔离: PostgreSQL RLS + 中间件强制租户过滤
- CSRF: SameSite Cookie + CSRF Token
- XSS: 标准 Web 安全防护（CSP 头）

### 5.3 兼容性需求
- PC: Chrome 90+, Edge 90+, Safari 15+
- H5: iOS Safari 15+, Android Chrome 90+
- 分辨率: PC 1280px+ / H5 375px+

## 9. 数据模型

### 9.1 核心表结构

**设计原则**：全局用户身份 + 租户自治密码（一个邮箱可在多个租户存在，每个租户独立管理密码）

```

├── id: UUID (PK)
├── email: VARCHAR(255) (UNIQUE)
├── name: VARCHAR(100)
├── avatar_url: VARCHAR(500)
├── email_verified: BOOLEAN (DEFAULT false)
├── created_at: TIMESTAMP
└── updated_at: TIMESTAMP

tenants（租户表）
├── id: UUID (PK)
├── name: VARCHAR(100)
├── slug: VARCHAR(50) (UNIQUE, 用于 URL)
├── logo_url: VARCHAR(500)
├── max_users: INT (DEFAULT 100)
├── max_apps: INT (DEFAULT 20)
├── max_org_levels: INT (DEFAULT 8)
├── status: ENUM('active', 'suspended')

├── created_at: TIMESTAMP
└── updated_at: TIMESTAMP

user_tenants（用户-租户关系表 — 含租户独立密码）
├── user_id: UUID (FK → users.id)

organizations（组织架构表）

applications（应用注册表）
├── id: UUID (PK)

├── icon_url: VARCHAR(500)

├── id: UUID (PK)
```

### 9.2 RLS 策略

```sql
-- 租户数据隔离：所有业务表必须包含 tenant_id
-- RLS 策略示例
CREATE POLICY tenant_isolation ON applications
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- users 表不需要 RLS（全局用户池，登录时按 email 查询）
-- user_tenants 表访问控制：
--   - 登录页：按 email 查询（无 RLS），返回用户所属的所有租户
--   - 登录后：按 tenant_id 过滤（有 RLS），只返回当前租户的成员
```

**user_tenants 访问控制细节**:
| 场景 | 查询方式 | RLS |
|------|---------|-----|
| 登录页查租户列表 | WHERE email = ? | 关闭（需要看到所有租户） |
| 登录后查当前租户成员 | WHERE tenant_id = ? | 开启（只看到当前租户） |
| 管理后台查成员列表 | WHERE tenant_id = ? | 开启（只看到当前租户） |

### 9.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 用户模型 | 全局用户身份 + 租户自治密码 | 租户独立管控账号安全，符合企业合规要求 |
| 密码存储 | 存在 user_tenants 表 | 每个租户独立管理密码，互不影响 |
| 租户隔离 | PostgreSQL RLS | 数据库层面强制隔离，安全性高 |
| 权限继承 | 取并集，只做加法 | 简单易理解，V1 不支持拒绝 |
| 用户-组织 | V1 一个用户一个主部门 | 简化实现，V1.1 支持兼任 |
| 应用嵌入 | iframe | 零侵入，应用无需改造 |

### 9.4 数据流示例

**登录流程（多租户场景）**:
```
1. 用户输入 email
2. 查询 user_tenants 获取用户所属租户列表
3. 如果 0 个租户 → 提示"该邮箱未被任何租户邀请"
4. 如果 1 个租户 → 直接进入密码输入页
5. 如果多个租户 → 显示租户选择器
6. 用户选择租户 → 进入密码输入页
7. 输入密码 → 查询 user_tenants 验证该租户下的密码
8. 密码正确 → 签发 JWT（含 tenant_id）
9. 密码错误 → 提示"密码错误"（不透露其他租户信息）
```

**注册流程（新用户被邀请）**:
```
1. 主租户管理员创建用户 → 输入邮箱、选择角色
2. 系统检查 users 表：
   - 如果邮箱已存在 → 直接在 user_tenants 添加记录
   - 如果邮箱不存在 → 创建 users 记录 + user_tenants 记录
3. 发送邀请邮件 → 用户点击链接设置密码
4. 密码存入 user_tenants.password_hash（该租户独立密码）
```

**数据访问流程**:
```
1. 请求到达 → 中间件从 Cookie 读取 current_tenant_id
2. 设置 PostgreSQL session: SET app.current_tenant_id = 'xxx'
3. 所有后续查询自动被 RLS 过滤
4. 只返回当前租户的数据
```

### 10.1 风险

| Prisma 与 RLS 配合 | 实现复杂度 | 中 | tenantMiddleware + 每表加 tenant_id 索引 |

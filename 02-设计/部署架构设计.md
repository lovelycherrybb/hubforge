# HubForge 部署架构设计

> 版本: v1.0
> 日期: 2026-07-27
> 作者: 设计师（架构负责人）

---

## 一、设计目标

HubForge 的部署架构必须满足三个核心场景：

| 场景 | 典型用户 | 说明 |
|------|---------|------|
| 单机部署 | 个人/小团队试用 | 一台机器跑全部组件，开箱即用 |
| 拆分部署 | 中小企业 | 数据库、应用、存储分别部署在不同机器 |
| 集群部署 | 生产环境/高可用 | 多实例负载均衡，数据库主从，存储分布式 |

**设计原则：组件可拆可合，通过配置切换，不改代码。**

---

## 二、系统组件拆分

HubForge 由 5 个独立可部署组件构成：

```
┌─────────────────────────────────────────────────────┐
│                    用户浏览器                         │
└──────────────┬──────────────────────────────────────┘
               │
       ┌───────▼───────┐
       │  反向代理/网关  │  ← Nginx / Traefik（可选）
       │  (Gateway)     │
       └───┬───────┬───┘
           │       │
    ┌──────▼──┐ ┌──▼──────────┐
    │ HubForge│ │  嵌入应用集群 │  ← 各业务应用
    │  Portal │ │  (App Pods)  │
    └────┬────┘ └─────────────┘
         │
    ┌────▼────┐    ┌──────────┐
    │ PostgreSQL│    │ 文件存储  │  ← 本地磁盘 / MinIO / S3
    │  (DB)    │    │ (Storage)│
    └─────────┘    └──────────┘
```

### 2.1 各组件职责

| 组件 | 职责 | 技术 | 默认端口 |
|------|------|------|---------|
| **Gateway** | SSL终止、路由分发、负载均衡、静态资源缓存 | Nginx / Traefik | 80/443 |
| **Portal** | HubForge 主门户（用户管理、权限、应用入口） | Next.js 14 | 3000 |
| **DB** | 数据持久化、RLS租户隔离 | PostgreSQL 16 | 5432 |
| **Storage** | 文件上传/下载（头像、附件等） | 本地磁盘 / MinIO | 9000 |
| **App Pods** | 各业务应用（iframe嵌入目标） | 任意技术栈 | 自定义 |

### 2.2 组件依赖关系

```
Portal ──依赖──→ DB（必须）
Portal ──依赖──→ Storage（可选，无上传功能时可省略）
Portal ──依赖──→ App Pods（可选，应用注册后才有）
App Pods ──可选依赖──→ DB（部分应用可能需要共享数据）
Gateway ──依赖──→ Portal + App Pods（反向代理目标）
```

**关键约束：Portal 是无状态的。** 认证信息全在 JWT Cookie 里，服务端不存 session。这意味着 Portal 可以水平扩展，不需要 sticky session。

## 三、三种部署模式

### 3.1 单机模式（Standalone）

**适用场景：** 个人试用、小团队、开发环境

**特点：** 一台机器，一个 docker-compose，5分钟启动。

```
┌──────────────────────────────────────┐
│            单台服务器                  │
│                                      │
│  ┌──────────┐  ┌──────────────────┐  │
│  │ Nginx    │  │ HubForge Portal  │  │
│  │ :80/443  │──│ :3000            │  │
│  └──────────┘  └────────┬─────────┘  │
│                         │            │
│  ┌──────────┐  ┌────────▼─────────┐  │
│  │ MinIO    │  │ PostgreSQL       │  │
│  │ :9000    │  │ :5432            │  │
│  └──────────┘  └──────────────────┘  │
│                                      │
│  ┌──────────────────────────────────┐│
│  │  业务应用 A / B / C              ││
│  │  :3001 / :3002 / :3003          ││
│  └──────────────────────────────────┘│
└──────────────────────────────────────┘
```

**docker-compose.standalone.yml：**
- Gateway: Nginx（可选，也可直接访问 :3000）
- Portal: HubForge Next.js
- DB: PostgreSQL（本地卷持久化）
- Storage: MinIO（可选）
- 应用容器: 各业务应用同机部署

**配置要点：**
```env
# 数据库 - 同机部署
DATABASE_URL=postgresql://postgres:postgres@postgres:5432/hubforge

# 存储 - 同机 MinIO 或本地磁盘
STORAGE_TYPE=local
STORAGE_PATH=/data/uploads
# 或
STORAGE_TYPE=minio
MINIO_ENDPOINT=http://minio:9000

# 应用地址 - 同机，用端口区分
# 在管理后台注册应用时，URL 填 http://localhost:3001
```

### 3.2 拆分模式（Split）

**适用场景：** 数据库独立服务器、应用和数据库分离

**特点：** 组件分散到不同机器，通过网络连接。

```
┌─────────────────┐    ┌─────────────────┐
│   应用服务器      │    │   数据库服务器    │
│                  │    │                  │
│  Nginx           │    │  PostgreSQL 16   │
│  HubForge Portal │───→│  :5432           │
│  业务应用 A/B/C   │    │                  │
│                  │    │  PgBouncer(可选) │
└─────────────────┘    └─────────────────┘
         │
         ▼
┌─────────────────┐
│   存储服务器(可选) │
│                  │
│  MinIO / NFS     │
│  :9000           │
└─────────────────┘
```

**配置要点：**
```env
# 数据库 - 远程服务器
DATABASE_URL=postgresql://user:pass@db-server:5432/hubforge

# 存储 - 远程 MinIO
STORAGE_TYPE=minio
MINIO_ENDPOINT=http://storage-server:9000
MINIO_ACCESS_KEY=xxx
MINIO_SECRET_KEY=xxx

# 应用地址 - 远程或同机
# 管理后台注册应用时填实际可访问的 URL
```

**与单机模式的区别：** 只改环境变量，代码零修改。

### 3.3 集群模式（Cluster）

**适用场景：** 生产环境、高可用、高并发

**特点：** 多实例负载均衡，数据库主从，存储分布式。

```
                    ┌──────────────┐
                    │  负载均衡器   │
                    │  (SLB/LB)   │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
       ┌──────▼─────┐ ┌───▼──────┐ ┌──▼────────┐
       │  Nginx #1  │ │ Nginx #2 │ │ Nginx #3  │
       └──────┬─────┘ └───┬──────┘ └──┬────────┘
              │            │            │
       ┌──────▼─────┐ ┌───▼──────┐ ┌──▼────────┐
       │  Portal #1 │ │Portal #2 │ │Portal #3  │
       │  :3000     │ │:3000     │ │:3000      │
       └──────┬─────┘ └───┬──────┘ └──┬────────┘
              │            │            │
              └────────────┼────────────┘
                           │
              ┌────────────┼────────────┐
              │                         │
       ┌──────▼──────┐         ┌───────▼──────┐
       │ PG 主库      │         │  MinIO 集群   │
       │ (读写)       │         │  (分布式)     │
       │ :5432        │         │  :9000        │
       └──────┬──────┘         └──────────────┘
              │
       ┌──────▼──────┐
       │ PG 从库      │
       │ (只读)       │
       │ :5432        │
       └─────────────┘

       ┌──────────────────────────────────────┐
       │         应用集群（独立节点）            │
       │  ┌─────────┐ ┌─────────┐ ┌─────────┐│
       │  │App A ×3 │ │App B ×2 │ │App C ×1 ││
       │  └─────────┘ └─────────┘ └─────────┘│
       └──────────────────────────────────────┘
```

**集群模式的关键技术决策：**

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 会话管理 | JWT Cookie（无服务端状态） | 天然支持水平扩展，不需要 Redis 存 session |
| 数据库连接 | PgBouncer 连接池 | 多实例共享连接池，避免连接数爆炸 |
| 文件存储 | MinIO 集群 / S3 | 分布式存储，多实例共享 |
| 应用路由 | Nginx location 分发 | 不同路径转发到不同应用集群 |
| 配置同步 | 环境变量统一注入 | K8s ConfigMap / Docker Swarm configs |

**集群配置要点：**
```env
# 数据库 - 通过 PgBouncer 连接
DATABASE_URL=postgresql://user:pass@pgbouncer:6432/hubforge

# 存储 - MinIO 集群
STORAGE_TYPE=minio
MINIO_ENDPOINT=http://minio-cluster:9000

# Portal 实例之间唯一区别：INSTANCE_ID（用于日志追踪）
INSTANCE_ID=portal-01
```

## 四、应用嵌入的部署适配

HubForge 的核心功能之一是通过 iframe 嵌入业务应用。应用的部署方式直接影响嵌入策略。

### 4.1 应用部署模式

| 模式 | 应用位置 | URL 示例 | 适用场景 |
|------|---------|---------|---------|
| 同机同域 | 和 Portal 同一台机器，同域名不同端口 | `http://host:3001` | 单机开发 |
| 同域不同机 | 不同机器，通过反向代理统一域名 | `https://portal.com/app/a/` | 生产环境推荐 |
| 跨域嵌入 | 独立域名 | `https://app-a.example.com` | 第三方应用 |

### 4.2 同域部署方案（推荐）

同域部署是 HubForge 的推荐方案——所有应用通过反向代理统一到同一域名下，iframe 可以共享 Cookie。

```
用户访问: https://portal.company.com

Nginx 路由规则:
  /                  → HubForge Portal (:3000)
  /app/inspection/   → 巡检应用 (:3001)
  /app/permit/       → 许可应用 (:3002)
  /app/xxx/          → 其他应用 (自定义端口)
```

**Nginx 配置示例：**
```nginx
upstream portal {
    server portal-1:3000;
    server portal-2:3000;  # 集群模式
}

upstream app-inspection {
    server app-inspection-1:3001;
    server app-inspection-2:3001;  # 应用也可集群
}

server {
    listen 443 ssl;
    server_name portal.company.com;

    # HubForge 主门户
    location / {
        proxy_pass http://portal;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 巡检应用
    location /app/inspection/ {
        proxy_pass http://app-inspection/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 其他应用按需添加...
}
```

### 4.3 应用 URL 注册

在 HubForge 管理后台注册应用时，URL 的填写规则：

| 部署模式 | 应用 URL 填写 | 说明 |
|---------|-------------|------|
| 单机同端口 | `http://localhost:3001` | 开发环境 |
| 单机反代 | `/app/inspection/` | 同域，用相对路径 |
| 跨域 | `https://app-a.example.com` | 完整 URL |

## 五、数据库部署方案

### 5.1 数据库可选方案

| 方案 | 部署方式 | 适用场景 | 连接串示例 |
|------|---------|---------|-----------|
| 本地 PG | Docker Compose 同机 | 单机/开发 | `postgresql://postgres:pass@postgres:5432/hubforge` |
| 独立 PG | 独立服务器安装 | 拆分部署 | `postgresql://user:pass@db-server:5432/hubforge` |
| 云数据库 | 阿里云 RDS / AWS RDS | 生产环境 | `postgresql://user:pass@rds-xxx.pg.rds.aliyuncs.com:5432/hubforge` |
| PG + PgBouncer | PG 前加连接池 | 集群模式 | `postgresql://user:pass@pgbouncer:6432/hubforge` |

### 5.2 Prisma 连接池配置

集群模式下多个 Portal 实例共享数据库，需要合理配置连接池：

```env
# 每个实例最多 10 个连接，3个实例 = 30 个连接
# PgBouncer 总连接池设为 100，留余量
DATABASE_URL="postgresql://user:pass@pgbouncer:6432/hubforge?connection_limit=10&pool_timeout=20"
```

### 5.3 RLS 在集群模式下的兼容性

当前 RLS 实现使用 `SET app.tenant_id`（会话级变量）。在连接池模式下需要注意：

- **Prisma 连接池**：每次请求独立连接，`SET` 和查询在同一连接内，**兼容**
- **PgBouncer transaction 模式**：同一事务内连接不变，**兼容**
- **PgBouncer session 模式**：需要确保 `SET` 在会话开始时执行，**兼容但需注意**

当前 `withTenantContext()` 的实现已经做了 SET → 操作 → RESET 的完整生命周期管理，在所有连接池模式下都能正确工作。

## 六、文件存储方案

### 6.1 存储抽象层

代码中需要一个存储抽象层，让业务逻辑不感知底层存储方式：

```typescript
// src/lib/storage.ts
interface StorageProvider {
  upload(key: string, data: Buffer, contentType: string): Promise<string>;
  download(key: string): Promise<Buffer>;
  delete(key: string): Promise<void>;
  getPublicUrl(key: string): string;
}

// 根据环境变量选择实现
// STORAGE_TYPE=local | minio | s3
```

| 存储类型 | 配置项 | 适用场景 |
|---------|-------|---------|
| `local` | `STORAGE_PATH` | 单机开发/小规模 |
| `minio` | `MINIO_ENDPOINT` + key/secret | 自建对象存储 |
| `s3` | `S3_ENDPOINT` + key/secret | 云上生产环境 |

### 6.2 存储迁移策略

从本地存储迁移到对象存储，只需：
1. 迁移文件到新存储
2. 改环境变量 `STORAGE_TYPE=minio`
3. 重启 Portal

业务代码无需修改。

## 八、部署操作手册

### 8.1 单机部署（5分钟）

```bash
# 1. 克隆项目
git clone <repo> hubforge && cd hubforge

# 2. 复制环境变量
cp deploy/standalone/.env.example .env
# 编辑 .env，修改 JWT_SECRET 和数据库密码

# 3. 一键启动
docker compose -f deploy/standalone/docker-compose.yml up -d

# 4. 初始化数据库
docker compose exec app npx prisma db push
docker compose exec app npx prisma db seed

# 5. 访问
open http://localhost:3000
```

### 8.2 拆分部署

```bash
# 数据库服务器
docker compose -f deploy/split/docker-compose.db.yml up -d

# 应用服务器（修改 .env 中 DATABASE_URL 指向数据库服务器）
docker compose -f deploy/split/docker-compose.app.yml up -d
```

### 8.3 集群部署

```bash
# 1. 数据库层（主从）
docker compose -f deploy/cluster/docker-compose.db.yml up -d

# 2. 存储层
docker compose -f deploy/cluster/docker-compose.storage.yml up -d

# 3. 应用层（可横向扩展实例数）
docker compose -f deploy/cluster/docker-compose.portal.yml up -d --scale portal=3

# 4. 网关层
# 配置 Nginx/Traefik，指向 portal 实例
```

## 九、横向扩展指南

### 9.1 Portal 扩展

Portal 是无状态的，直接加实例即可：

```bash
# 从 3 实例扩到 5 实例
docker compose -f deploy/cluster/docker-compose.portal.yml up -d --scale portal=5
```

### 9.2 应用扩展

每个业务应用独立扩展：

```bash
# 巡检应用从 1 扩到 3
docker compose -f deploy/cluster/docker-compose.apps.yml up -d --scale inspection=3
```

### 9.3 数据库扩展

- **读写分离**：主库写，从库读（需在代码层面区分读写操作）
- **连接池**：PgBouncer 管理连接数
- **分库**：未来按租户分库（当前阶段不需要）

## 十二、架构决策记录（ADR）

### ADR-001: 选择 JWT Cookie 而非服务端 Session
- **决策**: 认证信息全部存在 JWT Cookie 中
- **理由**: Portal 天然无状态，支持水平扩展，不需要 Redis
- **代价**: Token 有效期固定（24h），无法主动失效（需黑名单机制）
- **状态**: 已采纳

### ADR-002: 应用嵌入使用 iframe 而非微前端
- **决策**: 业务应用通过 iframe 嵌入 Portal
- **理由**: 技术栈无关（应用可以用任何语言/框架），隔离性好，开发成本低
- **代价**: 跨域通信受限（需 postMessage），样式无法统一
- **状态**: 已采纳

### ADR-003: 部署模式通过环境变量切换
- **决策**: 不同部署模式只改环境变量，不改代码
- **理由**: 同一套镜像适配所有环境，CI/CD 简单
- **代价**: 需要维护不同环境的 .env 文件

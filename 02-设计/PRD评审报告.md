## 二、问题清单（需修复）

### P0 — 必须修复（逻辑错误）

| # | 位置 | 问题 | 修复建议 |
|---|------|------|---------|
| 1 | M2 功能描述 | 写"每个租户有独立的用户池"，但数据模型已改为全局用户 | 改为"每个租户有独立的数据域，用户通过 user_tenants 关联" |
| 2 | M1 验收标准 | "支持邮箱+密码注册和登录" — 但现在是两步登录（先邮箱选租户，再输密码） | 改为"支持邮箱→选租户→密码的两步登录流程" |
| 3 | 密码锁定 | "错误密码 5 次后锁定 15 分钟" — 但密码是租户独立的，锁定范围不明确 | 明确为"单租户锁定"（只锁定当前租户的密码尝试） |

### P1 — 建议修复（边界场景）

| # | 位置 | 问题 | 修复建议 |
|---|------|------|---------|
| 4 | 记住我的选择 | 用户选择"记住 Tenant A"后，如果 Tenant A 停用或用户被移除，会卡在无效租户 | 增加校验：Cookie 中的 tenant_id 无效时，清除选择并重新走登录流程 |
| 5 | RLS 策略 | "user_tenants 表不需要 RLS" — 但用户能看到所有租户信息（包括不属于自己的租户） | 改为：登录页查询 user_tenants 时用 email 匹配（无 RLS），登录后查询用 tenant_id 过滤（有 RLS） |
| 6 | applications.slug | UNIQUE 约束未指定 tenant_id — 同一 slug 在不同租户应该允许 | 改为 UNIQUE(tenant_id, slug) |

### P2 — 可优化（文档完善）

| # | 位置 | 问题 | 修复建议 |
|---|------|------|---------|
| 7 | 注册流程 | PRD 范围写了"注册"，但流程只描述了"邀请"，没有自注册流程 | 明确：V1 是否支持自注册？还是纯邀请制？ |
| 8 | 切换租户 | 顶部栏"点击可切换" — 但切换租户后，当前页面数据会变，用户体验如何？ | 补充：切换租户后跳转到首页，不保留当前页面状态 |

## 三、测试验收（走查关键流程）

### 测试场景 1：新用户首次登录（单租户）

```
输入: admin@test.com（只在 Tenant A 存在）
期望: 输入邮箱 → 直接跳密码页 → 输密码 → 进入 Tenant A
实际: ✅ 流程正确
```

### 测试场景 2：多租户用户登录

```
输入: admin@test.com（在 Tenant A 和 Tenant B 都存在）
期望: 输入邮箱 → 显示租户选择器 → 选择 Tenant A → 输密码（Tenant A 的密码）→ 进入 Tenant A
实际: ✅ 流程正确
```

### 测试场景 3：密码错误

```
输入: admin@test.com → 选 Tenant A → 输错误密码
期望: 提示"密码错误"，不透露 Tenant B 的存在
实际: ✅ 流程正确
```

### 测试场景 4：忘记密码（多租户）

```
输入: admin@test.com → 点忘记密码 → 选 Tenant A → 收验证码 → 重置密码
期望: 只重置 Tenant A 的密码，Tenant B 的密码不变
实际: ✅ 流程正确
```

### 测试场景 5：租户邀请已有用户

```
输入: Tenant B 管理员邀请 admin@test.com（已存在于 Tenant A）
期望: 直接在 user_tenants 添加记录，发送邀请邮件，用户设置 Tenant B 的密码
实际: ✅ 流程正确
```

### 测试场景 6：密码锁定

```
输入: admin@test.com → 选 Tenant A → 连续 5 次输错密码
期望: Tenant A 锁定 15 分钟，但 Tenant B 仍可登录
实际: ⚠️ PRD 未明确锁定范围（问题 #3）
```

### 测试场景 7：记住选择后租户被停用

```
输入: 用户之前选择了"记住 Tenant A"，但 Tenant A 被管理员停用
期望: 清除无效选择，重新走登录流程
实际: ⚠️ PRD 未描述此场景（问题 #4）
```

### 测试场景 8：切换租户

```
输入: 用户在 Tenant A 的应用页面，点击顶部栏切换到 Tenant B
期望: 跳转到 Tenant B 首页
实际: ✅ 流程正确，但需补充"切换后跳首页"的说明（问题 #8）
```

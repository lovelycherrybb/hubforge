# HubForge 开发流程规范

> 版本: v1.0 | 日期: 2026-07-29
> 适用范围: HubForge 项目所有开发活动（AI agent + 人工）

---

## 一、核心理念

**明确标准 + 自动化检查 + 关键节点抽查**

- 机器能做的不靠人盯（lint / test / type check）
- CEO 只抓关键节点，不是每步都签字
- 流程服务于效率，不是反过来

---

## 二、任务分级

按**风险和影响面**分级，文件数仅作参考：

| 级别 | 定义 | 示例 | 流程 |
|------|------|------|------|
| **S（小修）** | 不影响逻辑，不涉及安全/数据 | typo、文案、样式微调、注释 | 直接改 → 通过基础检查 → commit |
| **M（中等）** | 改业务逻辑，范围可控 | bug 修复、功能优化、API 调整 | 需求确认 → 开发 → 验证 → commit |
| **L（大改）** | 改架构 / 涉及安全 / 数据库变更 / 新增模块 | 新功能、安全修复、DB migration | 需求确认 → 方案评审 → 开发 → 验证 → CEO 确认 |

**判断标准**（优先级从高到低）：
1. 涉及安全/权限/数据库 → 至少 M，通常 L
2. 改业务逻辑 → M
3. 仅改展示层/文案 → S

---

## 三、代码标准

### 3.1 Commit 规范

```
type: 简短描述（50字内）

[可选] 详细说明
```

类型：`feat` | `fix` | `refactor` | `style` | `docs` | `test` | `chore`

**单一目的**：一个 commit 只做一件事。

### 3.2 代码规范

- TypeScript strict mode
- ESLint 通过（`npx eslint src/`）
- 新代码必须有类型声明
- API 返回统一格式（使用 `src/lib/api-response.ts`）

### 3.3 测试规范

- 新 API 必须有测试用例
- 修复 bug 必须有回归测试
- 测试命令：`npx vitest run`

### 3.4 最低门槛（所有级别，含 S 级）

- `npx tsc --noEmit` 编译通过
- 不引入新的 lint warning

---

## 四、验证标准（按任务类型）

| 任务类型 | 验证方式 |
|----------|----------|
| UI / 前端 | 浏览器截图或预览，确认渲染正确 |
| API / 后端 | curl 测试或 vitest 用例，确认返回正确 |
| 数据库 | 查询验证，确认数据正确 |
| 安全修复 | 端到端测试，确认漏洞已修复且无回归 |
| 配置 / 部署 | 实际运行，确认服务正常 |

不要求所有任务都截图，按实际类型选择验证方式。

---

## 五、CEO 参与节点

CEO 只在以下节点参与：

| 节点 | 何时 | CEO 做什么 |
|------|------|------------|
| 需求确认 | L 级任务开始前 | 确认需求理解正确 |
| 方案评审 | L 级任务开发前 | 审批技术方案 |
| 验收确认 | L 级任务完成后 | 确认功能符合预期 |
| 部署确认 | 上线前 | 确认可以部署 |

**S / M 级任务不需要 CEO 参与，AI 自主完成。**

---

## 六、Git 分支策略

- **main 分支始终保持可部署状态**
- L 级任务：必须使用 feature 分支（`feat/xxx` 或 `fix/xxx`），完成后合并
- S / M 级任务：可直接在 main 提交，但需通过基础检查
- 禁止 force push 到 main

---

## 七、紧急通道（Hotfix）

生产环境出问题时：

```
发现问题 → CEO确认是P0 → 直接修复 → 验证 → 部署 → 事后补记录
```

不走正常流程，但必须：
1. CEO 确认是紧急问题
2. 修复后必须验证（编译 + 相关测试）
3. 事后补简要记录（改了什么、为什么紧急）

---

## 八、回滚机制

### 8.1 代码回滚

```bash
# Git 回滚
git revert HEAD
git push
```

### 8.2 Docker 回滚

```bash
# 停止当前容器，启动上一版本镜像
docker compose down
docker compose up -d  # 使用上一版本镜像标签
```

### 8.3 数据库回滚

- **Schema 变更**：使用 Prisma migrate 生成的 down migration，或手动编写回滚 SQL
- **RLS 策略变更**：`prisma/init.sql` 必须保持幂等（可重复执行不报错）
- **所有 L 级数据库变更必须附带回滚说明**，写在 commit message 或方案文档中

### 8.4 回滚决策流程

```
发现问题 → 评估影响 → CEO决策（回滚/热修） → 执行 → 验证 → 记录
```

## 九、自动化检查

### 已有

- TypeScript 编译检查：`npx tsc --noEmit`
- 测试套件：`npx vitest run`

### 建议补充

- ESLint：`npx eslint src/`
- 提交前自动运行（**pre-push hook**，不是 pre-commit）

### 不做的

- ❌ pre-commit 跑全量测试（太慢，影响开发体验）
- ❌ 强制关联任务 ID（当前无任务追踪系统）
- ❌ 多层审查报告（过度设计）

## 十、跨会话任务跟踪

在 `03-开发/TODO.md` 中维护进行中的 M / L 级任务：

```markdown
## 进行中

- [ ] [M] 修复 apps 路由 RLS 上下文缺失 — 开发中
- [ ] [L] 用户管理功能重构 — 待验收

## 已完成

- [x] [M] 登录页密码错误提示 — 2026-07-28
```

**规则**：
- M / L 级任务开始时必须写入 TODO.md
- 任务完成时移到"已完成"
- 新会话启动时先读 TODO.md 获取上下文

## 十一、执行示例

### S 级（小修）

```
你："这个文案改成xxx"
我：直接改 → tsc通过 → commit → 完成
```

### M 级（中等）

```
你："登录页密码错误没有提示"
我：确认理解 → 开发 → 测试验证 → commit → 告诉你完成
```

### L 级（大改）

```
你："加一个用户管理功能"
我：复述需求 → 你确认 → 出方案 → 你审批 → feature分支开发 → 验证 → 你确认 → 合并部署
```

### 紧急修复

```
你："生产环境挂了！"
我：确认P0 → 直接修复 → 验证 → 部署 → 事后记录
```

---

## 十二、总结

| 原则 | 说明 |
|------|------|
| 分级管理 | S/M/L 不同流程，不一刀切 |
| 机器优先 | lint / test / type check 自动化 |
| CEO 抓关键 | 只参与 L 级节点和部署确认 |
| 证据驱动 | 按类型提供验证证据，不强制截图 |
| 可回滚 | 代码 / 容器 / 数据库三层回滚 |
| 可追溯 | TODO.md 跨会话跟踪 |
